NetClone Architecture & Design

A local Netflix clone built to show a complete data platform: a Netflix-style web app with accounts, on top of a dimensional data warehouse and a DuckDB lakehouse, a two-stage recommender with a trained ranking model, semantic search, a natural-language assistant, an event-streaming pipeline, and adaptive video streaming with series episodes.

FastAPI SQLite star schema DuckDB + Parquet lakehouse scikit-learn (TF-IDF, SVD, learned ranker) pandas / numpy Kafka-style streaming Vanilla-JS SPA HLS video (ffmpeg + hls.js) Sessions + scrypt No cloud services

REAL app, accounts, data warehouse, lakehouse, ML models, ETL, analytics, streaming pipeline, adaptive HLS video   SIMULATED synthetic viewer history; titles and episodes play openly licensed stand-in films

01System architecture

One FastAPI process. The browser talks only to the JSON API (behind a sign-in guard) and the static media files; the API serves the recommender, the warehouse, the lakehouse and the streaming pipeline. Everything runs on localhost; the only optional network use is the one-time download of the films and, with a TMDB key, of poster art.

Figure 1. One process. The warehouse is the serving database; the lake keeps the raw history and the analytical tables.

02Frontend

A dependency-free single-page app (vanilla JS, no build step). api.js is a thin fetch wrapper (a 401 anywhere sends you back to sign-in); player.js is the video player; app.js holds the rest of the view logic and state. Frontend files are served with no-cache so browsers revalidate them after an update.

Accounts

Sign-in and sign-up screens, a "Who's watching?" gate with Add Profile (kids profiles never see mature titles), and an account menu to switch profile or sign out.

Home

A banner with the title's art and logo that starts a muted preview of the video after a few seconds, then rails: Continue Watching (episode-aware), My List, Top Picks, Trending, Critically Acclaimed, New Releases, "Because you watched X", genres, "Top 10 in your country".

Detail view

Synopsis, cast, warehouse stats, ratings, My List, "More Like This"; for a series, a season picker and an episode list with thumbnails and progress. Play starts or resumes the right episode.

Video player

Custom controls: seek bar with preview frames, back/forward 10 s, volume, subtitles, quality, full screen, keyboard shortcuts. Skip Intro and a Next Episode countdown for series.

Search and assistant

Live semantic search as you type; a chat panel that answers with poster cards (text is escaped, so a typed query can't inject markup).

Analytics

Warehouse KPIs and charts, the live streaming panel, the lakehouse layers and gold tables, and the recommender evaluation with the ranker's learned weights.

03Backend

FastAPI serves the SPA, the JSON API and the images. On startup it warms the recommender (including training the ranker), starts the streaming consumer, and runs the lakehouse once in the background. Singletons are created lazily and shared across requests.

  • main.py - routes, Pydantic request models, model/streaming/lakehouse bootstrap, static mount.
  • auth.py - sessions, the sign-in routes, profile management, and the guard in front of /api.
  • episodes.py - seasons, the episode Play should start (resume, next, or the first), the next episode.
  • store.py - operational writes (watch events, ratings, My List) and Continue Watching.
  • video.py - /api/play/{id} and the /media/* file server.
  • artwork.py / poster.py - TMDB art when it has been downloaded, a generated SVG otherwise. Image URLs carry the art's version, so new art shows up without a stale browser cache.

04Accounts and security

Every /api call goes through a guard (plain ASGI middleware) that needs a signed-in session, apart from the sign-in calls and the images. A call that names a profile_id, in the query string or the JSON body, must name a profile on the signed-in account; the guard reads the body, checks it, and hands it on untouched, so the route functions themselves don't change.

Figure 2. Every API call is checked before it reaches a route.
  • Passwords are hashed with scrypt (standard library) and a random salt per password, and compared in constant time. A wrong email takes as long as a wrong password.
  • Sessions are a random 256-bit token in an HttpOnly, SameSite=Lax cookie (page scripts can't read it; other sites can't make the browser send it with a POST). Only its SHA-256 is stored, so a copy of the database holds no usable sessions. They last 30 days.
  • Rate limiting: five failed sign-ins for an email in ten minutes and further attempts get 429.
  • Through rebuilds: app_account and app_session are operational tables the ETL never drops, and people who sign up get user and profile ids from 100000, clear of the generated population, so a rebuild regenerates everything else and puts them back.

05Data engineering

A logged, idempotent ETL builds a Kimball-style dimensional model. A seeded generator simulates a viewer population with latent genre tastes, producing an interaction log for the models to learn from. The warehouse carries a schema version; an older one is rebuilt automatically after a schema change.

ETL stages

StageWhat happens
ExtractCurated catalog (61 titles, with real season sizes for the 32 series) + a generated population of ~280 viewers. A film session is one watch event; a series session is a binge of consecutive episodes, picking up where the viewer left off.
TransformSurrogate keys, 855 episodes, derived attributes (decade, weekend flag), genre normalisation into a bridge table, a calendar date dimension.
LoadBulk insert into the SQLite star schema. App-made users and profiles are kept and put back; the demo login is created if missing.
EnrichIf TMDB data has been fetched, real episode names and synopses replace "Episode N".
Validate21 checks: referential integrity (events to titles, profiles, dates, episodes), value ranges, null/blank, uniqueness, every series has episodes numbered 1..n per season, an event's episode belongs to its title, lineage values, every login belongs to a user. The run fails if any check fails.

External source: TMDB

data_engineering/tmdb.py treats TMDB as an optional source system. With a free API key it matches each title by name, year and type (within a year, so a made-up title never borrows another film's poster), downloads posters, banners, title logos and episode stills into data/tmdb/ with a manifest, and copies episode names and synopses into dim_episode. The ETL re-applies them on every rebuild, and the app serves everything locally afterwards.

06Lakehouse

Beside the serving warehouse sits a lakehouse: Parquet files in three layers, built and queried with DuckDB. Live events reach it straight from the event stream, through its own consumer group, so the warehouse and the lake read the same topics independently. A run takes about half a second.

Figure 4. Bronze keeps what arrived, silver makes it trustworthy, gold answers business questions.
  • Bronze copies the warehouse's generated history once (and again only if its fingerprint changes) and drains new stream records each run. Offsets are committed only after the batch file is written, so a crash means re-reading a batch, never losing one.
  • Silver drops duplicates (a re-delivered batch is in bronze twice but in silver once), checks every row against the dimension snapshots, and sends failures to a quarantine table with the reason, such as series event without an episode from before episodes existed.
  • Gold includes a sessionisation query: window functions find where a viewer's next episode started more than 30 minutes after the previous one ended, which splits binges into sessions.
  • Because bronze keeps every streamed event, the lake still has live activity after the warehouse has been rebuilt.

07AI / ML

The recommendation service trains real models on startup from the warehouse and exposes the rails the home page uses. All models are classical ML (scikit-learn and numpy); there are no external LLM calls.

Content-based TF-IDF

Each title becomes a TF-IDF vector over its metadata blob (genres ×3, keywords ×2, cast, director, description, decade). Cosine similarity drives "More Like This" and a per-profile taste vector.

Collaborative filtering SVD item-item ALS

From the implicit-feedback matrix (profiles × titles, valued by an engineered affinity score in film-sized units: six episodes weigh like one film): truncated SVD predicts affinity, item-item cosine gives "people who watched A also watched B", and implicit ALS (Hu-Koren) feeds the ranker.

Semantic search NL intent

TF-IDF vector space plus a parser that extracts structured intent (decade, movie/series, genre, mood synonyms like scary -> Horror) and applies it as a soft boost.

AI Concierge rule-based

Classifies intent (recommend / similar / info / mood / search) and routes to the recommender or search engine, composing a reply that cites real titles.

Two-stage ranking

Top Picks come from two stages. A hybrid blend of four normalised signals shortlists 40 candidates (with a cold-start fallback to trending and kids/maturity filtering):

hybrid = 0.40 · content-based
     + 0.30 · item-item collaborative ("co-viewed")
     + 0.20 · matrix-factorization (SVD)
     + 0.10 · popularity (viewers + views)

A trained ranker then orders the shortlist. It is pairwise (the RankNet idea with a linear scorer): each profile's latest titles are held out, the base models are refitted on the history before them, and the ranker learns weights that score watched titles above unwatched ones from the same profile. Its features are the model scores plus how the profile's genre taste compares with the catalog and with other viewers, the films-vs-series habit, title age and IMDb score. Gradient-boosted trees were tried first and overfit on this data.

Figure 5. The hybrid finds candidates; the trained ranker orders them; MMR keeps the row varied.

Offline evaluation

A leakage-free per-profile holdout retrains every model on the train split only, ranks the held-out titles, and scores each with Precision@K, Recall@K, NDCG@K, MAP@K, hit rate and catalog coverage (ai/evaluation.py, GET /api/eval, the Analytics page). On a freshly built warehouse, at K = 10:

The ranker comes out level with the hand-designed hybrid: on the same 558 profiles the NDCG@10 difference is -0.005, with a 95% interval of -0.017 to +0.007 (paired bootstrap); it ranks better for 30% of profiles and worse for 35%. It learned that blend from data rather than having it picked, and it reaches more of the catalog. Both beat every single model. USE_RANKER in recommender.py switches Top Picks back to the hybrid alone.

Live feedback loop

Watching or rating updates the in-memory profile state immediately (the ranker reads it too), so "Top Picks" and "Because you watched" re-rank without a full retrain. POST /api/admin/refresh retrains every model, the ranker included, from the current warehouse.

08Event streaming

Watch and rating actions are not written to the database directly. The API produces them to a log. One consumer group (warehouse-sink) maintains a time-windowed live trending tally and sinks each event into the warehouse while updating the live recommender state; a second (lake-sink) lands the same events in the lakehouse's bronze layer, at its own pace.

Figure 6. One log, two independent consumer groups. The same pipeline runs on the in-process log broker or a real Kafka broker.

Two interchangeable backends

backends.py selects the backend at startup and exposes one interface (producer, consumer, stats), so the consumer / sink / trending code is identical for both:

  • In-process log broker (default) - pure Python, no install. Topics are partitioned, append-only logs persisted to .log files (replayable across restarts); consumer groups commit offsets independently, and two processes sharing the offsets file never move each other's offsets backwards.
  • Apache Kafka - set KAFKA_BOOTSTRAP (or run python run.py --kafka) with the provided single-node Kafka in Docker (KRaft, no Zookeeper). On startup the app probes the broker; if reachable it uses Kafka and creates the topics, otherwise it falls back to the log broker so the app always runs. The active backend is shown on the Analytics page.

09Video streaming

Playback is adaptive HLS, the approach real streaming services use. Each film is cut into 4-second segments at up to three qualities, and the player picks the quality segment by segment based on measured bandwidth. The catalog titles are copyrighted, so every title, and every episode of a series, plays one of three openly licensed Blender films (Big Buck Bunny, Elephants Dream, Tears of Steel), credited on screen. Consecutive episodes play different films.

Figure 7. Each film becomes a quality ladder plus the extras the player uses.
  • Ingest (python -m media.ingest) downloads each film, then ffmpeg encodes every quality in one pass. A keyframe is forced at each segment boundary so all qualities line up and switching never glitches. If a download fails, a generated test-pattern clip is used instead.
  • Extras (python -m media.extras, also run by ingest): seek-bar preview sprites with a WebVTT index, made in seconds by decoding keyframes only; a set of stills for episode thumbnails (near-black fade frames are measured and dropped); Tears of Steel's official subtitles in nine languages, converted from SRT to WebVTT; and each film's opening-titles and end-credits times, read off frame grabs.
  • Serving: /api/play/{id} picks the episode for a series (the one asked for, or the one in progress, the next one, or the first), and returns the master playlist URL, duration, resume point, subtitles, preview index, intro/credits marks and the next episode. Everything else is static files under /media/.
  • Playback: hls.js (vendored) feeds the segments to the browser's <video> behind custom controls. Subtitles are parsed by the browser and drawn by the player so they sit above the controls. Skip Intro shows during the opening titles; from the end credits a Next Episode countdown plays the next one by itself, and reaching the credits counts as finishing. The player reports real seconds watched (seeks excluded). With no converted video, the same controls drive a fast-forward simulation.

11Running it

# optional: install dependencies
pip install -r requirements.txt

# build the warehouse on first launch, then start the server
python run.py
# open http://127.0.0.1:8000 and sign in with the demo account (README) or sign up

# other commands
python run.py --rebuild          # force-rebuild the warehouse (accounts are kept), then serve
python run.py --etl              # run the ETL pipeline only
python -m lakehouse.build        # bronze -> silver -> gold
python -m ai.evaluation          # offline recommender metrics
python -m streaming.pipeline     # standalone streaming demo (throwaway broker)

# real video (one-time, about 645 MB of downloads)
python -m media.ingest                  # download films, build HLS streams and extras
python -m media.ingest --placeholder    # offline: generated test-pattern clips
python -m media.extras                  # extras for films converted earlier

# real poster art (optional, free TMDB key in .env)
python -m data_engineering.tmdb

# real Kafka backend (optional)
docker compose up -d      # single-node Kafka on localhost:9092
python run.py --kafka     # app uses the real broker
docker compose down

Data generation is seeded, so every rebuild reproduces the same warehouse. Delete data/netflix.db and relaunch to regenerate from scratch.
