NetClone Architecture & Design

A local, fully offline Netflix clone built to showcase a complete data platform: a Netflix-style web app on top of a dimensional data warehouse, a hybrid recommender, semantic search, a natural-language assistant, and an event-streaming pipeline.

FastAPI SQLite star schema scikit-learn (TF-IDF + SVD) pandas / numpy Kafka-style streaming Vanilla-JS SPA HLS video (ffmpeg + hls.js) No cloud · no internet

REAL app, data warehouse, ML models, ETL, analytics, streaming pipeline, adaptive HLS video   SIMULATED synthetic viewer history; titles play openly licensed stand-in films

01System architecture

Three layers behind one FastAPI process. The browser talks only to the JSON API; the API serves the recommender, the warehouse, and the streaming pipeline. Everything runs on localhost.

Figure 1. All layers run in one process; the SQLite warehouse is the shared source of truth.

02Frontend

A dependency-free single-page app (vanilla JS, no build step). api.js is a thin fetch wrapper; player.js is the video player; app.js holds the rest of the view logic and state.

Profiles

"Who's watching?" gate. Recommendations are per-profile; a Kids profile filters out mature content.

Hero banner + personalised rails: Continue Watching (with a resume bar), Top Picks, Trending, Critically Acclaimed, New Releases, "Because you watched X", genre rows, and "Top 10 in your country".

Detail modal

Synopsis, cast, real warehouse stats (viewers / watch-hours / completion), rating buttons, My List, "More Like This".

Video player

Adaptive HLS playback with a quality picker and resume. Reports the seconds actually watched, which feeds the recommender and Continue Watching.

Search

Live semantic search as you type.

AI Concierge

Chat panel that returns grounded recommendations with poster cards.

Analytics

KPI cards, bar charts from the warehouse, and the live streaming-pipeline panel.

Posters

Every title's key art is a procedurally generated SVG - no external image assets.

03Backend

FastAPI serves the SPA, the JSON API, and the procedural posters. On startup it warms the recommender models and starts the streaming consumer. Singletons are created lazily and shared across requests.

  • main.py - routes, Pydantic request models, model/streaming bootstrap, static mount.
  • store.py - operational writes (watch events, ratings, My List) into the warehouse.
  • video.py - /api/play/{id} (stream URL, duration, resume point) and the /media/* file server for HLS playlists and segments.
  • poster.py - deterministic SVG poster from each title's stored hue + metadata.

04Data engineering

A logged, idempotent ETL builds a Kimball-style dimensional model. Since the clone is offline, a seeded generator simulates a viewer population with latent genre tastes, producing a realistic interaction log for the models to learn from.

Validate13 data-quality checks - referential integrity, value ranges, null/blank, uniqueness, "every title has a genre". The run fails if any check fails.

05AI / ML

The recommendation service trains real models on startup from the warehouse and exposes the rails the home page uses. All models are classical ML (scikit-learn) - no external LLM calls.

Content-based TF-IDF

Each title becomes a TF-IDF vector over its metadata blob (genres ×3, keywords ×2, cast, director, description, decade). Cosine similarity drives "More Like This" and a per-profile taste vector. Matrix: ~61 × 3.3k features.

Collaborative filtering SVD item-item ALS

From the implicit-feedback matrix (profiles × titles, valued by an engineered affinity score): Truncated SVD with 24 latent factors predicts affinity for unseen titles; item-item cosine gives "people who watched A also watched B". A pure-numpy implicit ALS (Hu-Koren) is also implemented and benchmarked against the others.

Semantic search NL intent

TF-IDF vector space plus a parser that extracts structured intent (decade, movie/series, genre, mood synonyms like scary -> Horror) and applies it as a soft boost.

AI Concierge rule-based

Classifies intent (recommend / similar / info / mood / search) and routes to the recommender or search engine, composing a reply that cites real titles.

Hybrid ranker

The personalised list blends four normalised signals, with a cold-start fallback to trending and per-profile kids/maturity filtering:

final_score = 0.40 · content-based
      + 0.30 · item-item collaborative ("co-viewed")
      + 0.20 · matrix-factorization (SVD)
      + 0.10 · global popularity prior
Figure 3. Hybrid recommendation pipeline. Cold start (no history) falls back to trending.

Diversity re-ranking

Top Picks are re-ranked with MMR (maximal marginal relevance): each pick trades relevance against content-similarity to the already-chosen titles, so the rail is not dominated by one genre.

Offline evaluation

There is an offline eval for the recommender (ai/evaluation.py). A leakage-free per-profile holdout retrains every model on the train split only, ranks the held-out items, and scores each with Precision@K, Recall@K, NDCG@K, MAP@K, hit-rate and catalog coverage. On the same split the hybrid wins (NDCG@10 ≈ 0.26, ahead of item-item, content, popularity, SVD and ALS); popularity has the lowest coverage. A grid search can tune the blend weights. Exposed at GET /api/eval and python -m ai.evaluation.

Live feedback loop

Watching or rating updates the in-memory profile state immediately, so "Top Picks" and "Because you watched" re-rank without a full retrain. POST /api/admin/refresh retrains every model from the current warehouse.

06Event streaming

Watch and rating actions are not written to the database directly. The API produces them to a log; a background consumer reads the log, maintains a time-windowed live trending tally, and sinks each event into the warehouse while updating the live recommender state.

Figure 4. Event flow. The same pipeline runs on the in-process log broker or a real Kafka broker.

Two interchangeable backends

backends.py selects the backend at startup and exposes one interface (producer, consumer, stats), so the consumer / sink / trending code is identical for both:

  • In-process log broker (default) - pure Python, no install. Topics are partitioned, append-only logs persisted to .log files (replayable across restarts); consumer groups commit offsets independently. This models Kafka's concepts offline.
  • Apache Kafka - set KAFKA_BOOTSTRAP (or run python run.py --kafka) with the provided single-node Kafka in Docker (KRaft, no Zookeeper). On startup the app probes the broker; if reachable it uses Kafka and creates the topics, otherwise it falls back to the log broker so the app always runs. The active backend is shown on the Analytics page.

07Video streaming

Playback is adaptive HLS, the approach real streaming services use. Each film is cut into 4-second segments at up to three qualities, and the player picks the quality segment by segment based on measured bandwidth. The catalog titles are copyrighted, so every title plays one of three openly licensed Blender films (Big Buck Bunny, Elephants Dream, Tears of Steel), credited on screen.

Figure 5. Each film becomes a quality ladder the player switches between as bandwidth changes.
  • Ingest (python -m media.ingest) downloads each film, then ffmpeg encodes every quality in one pass. A keyframe is forced at each segment boundary so all qualities line up and switching never glitches. A film only gets the qualities that fit its own resolution. If a download fails, a generated test-pattern clip is used instead, so the pipeline also works offline.
  • Serving: /api/play/{id} maps the title to a film and returns the master playlist URL, the duration, and a resume point (the same started-but-unfinished rule as Continue Watching). The playlists and segments are static files under /media/.
  • Playback: hls.js (vendored, so it works offline) feeds the segments to the browser's <video>; Safari uses its native HLS support. The player counts real seconds watched (seeks excluded) and posts them as a watch event, so the recommender and Continue Watching react to actual viewing. With no ingested video it falls back to simulated playback.

09Running it

# optional: install dependencies
pip install -r requirements.txt

# build the warehouse on first launch, then start the server
python run.py
# open http://127.0.0.1:8000

# other commands
python run.py --rebuild   # force-rebuild the warehouse, then serve
python run.py --etl       # run the ETL pipeline only
python -m streaming.pipeline   # standalone streaming demo

# real video (one-time, about 645 MB of downloads)
python -m media.ingest                  # download films, build HLS streams
python -m media.ingest --placeholder    # offline: generated test-pattern clips

# real Kafka backend (optional)
docker compose up -d      # single-node Kafka on localhost:9092
python run.py --kafka     # app uses the real broker
docker compose down

Data generation is seeded, so every rebuild reproduces the same warehouse. Delete data/netflix.db and relaunch to regenerate from scratch.
